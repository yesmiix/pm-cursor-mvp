# Runbook

Операционные инструкции для PM Cursor MVP: как разбираться с проблемами на проде и что делать при инцидентах.

---

## 1. Если на проде ошибка (UI / 5xx / таймауты)

1. **Открыть Vercel → Project → Deployments → Runtime Logs**
   - Посмотри последние логи для прод‑деплоя.
   - Обрати внимание на:
     - ошибки из `app/api/design/route.ts` (`Unexpected error in /api/design`, `LLM error response`, проблемы с env);
     - ошибки из `app/api/kb/*` и `app/api/ask/route.ts` (RAG: embeddings, storage, chat);
     - ошибки Next.js/Node (OOM, timeout, 500 и т.п.).
2. **Проверить env vars**
   - На Vercel во вкладке *Settings → Environment Variables* убедись, что заданы:
     - `LLM_API_KEY`;
     - `LLM_BASE_URL`;
     - `LLM_MODEL` (опционально, по умолчанию `gpt-4o-mini`).
   - Для One-doc RAG (страницы `/kb`, `/ask`):
     - `EMBEDDING_MODEL` (опционально, по умолчанию `text-embedding-3-small`);
     - для персистентного хранения документа на проде: `KV_REST_API_URL`, `KV_REST_API_TOKEN` (Vercel KV). Без них данные RAG хранятся in-memory и не сохраняются между запросами.
   - Если что‑то менял локально — синхронизируй с Vercel и сделай новый деплой.
3. **Проверить размер payload (количество и размер изображений)**
   - В логах можешь увидеть ошибки от Vercel (лимит body) или LLM‑провайдера.
   - Если пользователь отправляет много тяжёлых картинок, порекомендуй сократить количество/размер.
4. **Повторить локально**
   - Скопируй пример payload из логов (или попроси пользователя).
   - Локально:
     ```bash
     npm install
     npm run dev
     # или npm run build && npm run start
     ```
   - Повтори запрос к `http://localhost:3000/api/design` тем же телом.
   - Если проблема воспроизводится локально — проще дебажить и менять код.
5. **Зафиксировать результат**
   - После фикса обнови:
     - `CHANGELOG.md` — добавь запись с версией и описанием исправления;
     - `RUNBOOK.md` — кратко опиши, как воспроизвести и как исправить.

## 2. Типовые проблемы и решения

### 2.1. Пользователь видит «LLM_API_KEY или LLM_BASE_URL не заданы»

**Причина:** не выставлены или неправильно заданы env‑переменные.

**Действия:**
1. Проверить `.env.local` (локально) или env в Vercel.
2. Убедиться, что:
   - `LLM_BASE_URL` без лишнего хвостового `/` (хотя код его и обрезает).
   - Ключ `LLM_API_KEY` валидный и не протухший.
3. Перезапустить локальный сервер или запустить новый деплой на Vercel.

---

### 2.2. Ответ от LLM с ошибкой (`LLM error response`)

**Симптомы:**
- В UI выводится текст ошибки из LLM (rate limit, bad request, auth error и т.п.).
- В логах Vercel — `LLM error response: { ... }`.

**Действия:**
1. В логах посмотреть полный JSON ответа LLM.
2. Проанализировать:
   - статус (401, 429, 5xx);
   - `error.message` или `message`.
3. В зависимости от статуса:
   - `401/403` — проверить ключ, права, billing;
   - `429` — уменьшить частоту запросов, подождать, при необходимости добавить в UI дружелюбное сообщение о лимитах;
   - `400` — проверить, не слишком ли большой `messages`/payload или нет ли неподдерживаемых полей;
   - `5xx` — проблема на стороне провайдера, повторить попытку позже.

---

### 2.3. Лимиты размера payload (большие изображения)

**Симптомы:**
- 413/414 от Vercel/прокси;
- таймауты или 5xx от LLM‑провайдера;
- резкое увеличение времени ответа.

**Действия:**
1. В логах посмотреть размер тела запроса (если логируешь) и пример.
2. Рекомендовать пользователю:
   - уменьшить количество изображений;
   - уменьшить разрешение/размер файлов.
3. Как улучшение:
   - добавить в UI предварительную проверку размера и количества картинок;
   - показывать понятное сообщение об ограничениях до отправки.

---

### 2.4. One-doc RAG: «Документ не загружен» / ошибки на /ask

**Симптомы:**
- На странице `/ask` при нажатии «Спросить» — ошибка «Документ не загружен или эмбеддинги не готовы».
- Или ошибка от embeddings/chat API (ключ, модель, лимиты).

**Действия:**
1. Убедиться, что пользователь сначала сохранил документ на `/kb` (кнопка «Сохранить документ»).
2. Проверить env: `LLM_API_KEY`, `LLM_BASE_URL` (нужны и для embeddings, и для chat); при необходимости `EMBEDDING_MODEL`.
3. На проде без KV документ живёт только в памяти инстанса; после холодного старта или другого инстанса данных нет — нужно снова сохранить документ на `/kb` или подключить Vercel KV (`KV_REST_API_URL`, `KV_REST_API_TOKEN`).
4. В логах смотреть ошибки из `app/api/kb/set/route.ts` (при сохранении), `app/api/ask/route.ts` (при вопросе); типично — ошибка от внешнего API embeddings или chat.

## 3. Деплой и откат

### 3.1. Стандартный деплой

1. Вносишь изменения → обновляешь `CHANGELOG.md` и `TODO.md`.
2. Коммитишь в `main` или мёржишь PR в `main`.
3. Vercel автоматически запускает деплой.
4. Проверяешь:
   - статус деплоя;
   - Runtime Logs (нет ли критичных ошибок);
   - UI на проде: `/`, `/user-segments`, `/kb`, `/ask`, `/backlog` (при необходимости — сохранить документ на `/kb`, затем Generate на `/backlog` или вопрос на `/ask`).

### 3.2. Откат

1. В Vercel в списке деплоев выбрать последний **стабильный** деплой.
2. Нажать **Promote to Production**.
3. Зафиксировать в `CHANGELOG.md`, что был откат и почему.

---

## 4. Когда обновлять Runbook

- Поймал новый тип инцидента → добавь сюда:
  - как воспроизвести;
  - как диагностировать (где смотреть логи);
  - как исправить;
  - какие изменения в коде докинули.
- Если меняется архитектура (`/api/design`, `/api/kb/*`, `/api/ask`, `/api/backlog/*`, формат запросов, env) — обязательно обнови соответствующие секции.

Этот файл должен оставаться максимально прикладным: открываешь его во время инцидента и по шагам доходишь до решения.
